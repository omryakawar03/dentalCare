# Implementation guide (Hinglish)

Yeh 30-step delivery order hai. Pehle synthetic data aur ek pilot municipality use karein. Har production gate municipal legal/security approval ke baad hi pass hoga. Commands project folder ke andar chalayein. API dev command ke liye `cd apps/api`; web/mobile ke liye respective folders.

1. **Requirements** — **WHAT:** services, roles, language, data classes, SLAs likhein. **WHY:** scope aur legal basis clear rahe. **HOW:** ward officers/citizens ke saath process map karein. **FILES:** `docs/`, service catalogue. **COMMANDS:** `git status`. **SECURITY:** data inventory, consent/legal basis. **TESTING:** stakeholder sign-off aur acceptance criteria.
2. **Repository structure** — **WHAT:** API/web/mobile/docs/infra alag rakhein. **WHY:** teams independently deliver kar sakein. **HOW:** is scaffold ko base banayein. **FILES:** `apps/*`, `infra/`, `docs/`. **COMMANDS:** `git ls-files`. **SECURITY:** secrets `.gitignore` mein. **TESTING:** clean checkout se setup repeat karein.
3. **Frontend setup** — **WHAT:** citizen/admin responsive portal. **WHY:** phone aur desktop dono par usable. **HOW:** Next.js app run karke approved API connect karein. **FILES:** `apps/web/src/app`. **COMMANDS:** `pnpm install; pnpm dev`. **SECURITY:** browser mein secrets nahi, CSP/CORS. **TESTING:** keyboard, screen-reader, mobile viewport review.
4. **Mobile setup** — **WHAT:** Android-first Expo app. **WHY:** low-connectivity citizen access. **HOW:** app shell mein routing, API client, localization add karein. **FILES:** `apps/mobile`. **COMMANDS:** `pnpm install; pnpm start`. **SECURITY:** secure token storage, minimum offline cache. **TESTING:** real low-end Android/device/network checks.
5. **Backend setup** — **WHAT:** FastAPI modular API. **WHY:** clients ko stable versioned interface mile. **HOW:** routers/service/repository/schema boundaries banayein. **FILES:** `apps/api/app`. **COMMANDS:** `pip install -e '.[dev]'; uvicorn app.main:app --reload`. **SECURITY:** headers, size/time limits, input validation. **TESTING:** OpenAPI contract and health checks.
6. **Database** — **WHAT:** PostgreSQL/PostGIS schema. **WHY:** normalized data aur spatial complaints. **HOW:** local DB start karke migration apply karein. **FILES:** `migrations/`, `docs/architecture/database.md`. **COMMANDS:** `docker compose up -d db; alembic upgrade head`. **SECURITY:** private subnet, encryption, tenant RLS. **TESTING:** migration/restore and query-plan review.
7. **Authentication** — **WHAT:** verified OTP or approved IdP. **WHY:** account ownership. **HOW:** rate-limited OTP provider, rotating session, revoke flows integrate karein. **FILES:** API auth module (to implement). **COMMANDS:** provider-specific. **SECURITY:** OTP brute-force throttling, Argon2id/MFA, refresh reuse detection. **TESTING:** abuse, lockout and recovery scenarios.
8. **RBAC** — **WHAT:** roles + ward/department/resource scope. **WHY:** least-privilege administration. **HOW:** claims se trusted tenant context bind karke har query scope karein. **FILES:** `app/security/scope.py`, RBAC migration. **COMMANDS:** migration commands above. **SECURITY:** deny by default; no inherited PII at parent levels. **TESTING:** cross-tenant and ward access attempts.
9. **Citizen module** — **WHAT:** own profile/services/complaints. **WHY:** citizens apna data safely dekhein. **HOW:** `/citizens/me` and consent-controlled fields. **FILES:** API routes, web/mobile screens. **COMMANDS:** `pnpm dev`. **SECURITY:** self-only, masking, access audit. **TESTING:** two-user isolation and revoke consent.
10. **Household module** — **WHAT:** verified households/family links. **WHY:** authorized civic service delivery. **HOW:** duplicate review, evidence workflow, change approvals. **FILES:** schema and household routes. **COMMANDS:** Alembic revision/upgrade. **SECURITY:** restricted classification and field-level visibility. **TESTING:** approval, rollback, household membership privacy.
11. **Ward module** — **WHAT:** ward configuration and scoped totals. **WHY:** delegated operations. **HOW:** admin-configured boundaries and aggregates. **FILES:** `wards`, GIS setup. **COMMANDS:** migration/seed synthetic fixtures. **SECURITY:** no boundary-based identity inference. **TESTING:** aggregate scope per ward.
12. **Complaint system** — **WHAT:** submit, assign, status history, reopen. **WHY:** traceable grievance resolution. **HOW:** state machine, idempotent create and queue events. **FILES:** complaint routes/services/models. **COMMANDS:** local API startup. **SECURITY:** attachment quarantine, location minimization, anonymous policy. **TESTING:** complete lifecycle and unauthorized transition.
13. **Admin dashboard** — **WHAT:** scoped operational metrics. **WHY:** workload visibility. **HOW:** aggregates server-side, with freshness/source. **FILES:** `apps/web/src/app/admin`. **COMMANDS:** `pnpm dev`. **SECURITY:** role guarded on server/API. **TESTING:** verify row and aggregate scope.
14. **Notifications** — **WHAT:** push/SMS/email adapters. **WHY:** citizens get status changes. **HOW:** queued templates, delivery callbacks, preference controls. **FILES:** worker/provider modules (to implement). **COMMANDS:** provider sandbox commands. **SECURITY:** opt-outs, no PII in lock-screen text. **TESTING:** retry, duplicate, failure and suppression.
15. **Emergency** — **WHAT:** verified official contact registry. **WHY:** one-tap reliable guidance. **HOW:** configure only source-checked numbers and approval dates. **FILES:** `emergency_contacts`. **COMMANDS:** admin workflow. **SECURITY:** no fabricated numbers; explicit location consent. **TESTING:** stale-number approval/disable flow.
16. **AI assistant** — **WHAT:** multilingual retrieval answer. **WHY:** approved service info easier to find. **HOW:** ingest versioned authoritative FAQs; abstain when source absent. **FILES:** `docs/ai/` (create) and gateway. **COMMANDS:** provider-specific. **SECURITY:** PII redaction, injection boundaries, retention review. **TESTING:** grounding/abstention and prompt-injection evaluations.
17. **AI analytics** — **WHAT:** complaint classification/trends. **WHY:** staff can prioritize patterns. **HOW:** async suggestions with source/confidence; officer decides. **FILES:** AI gateway + analytics jobs. **COMMANDS:** worker startup. **SECURITY:** no binding decisions/actions. **TESTING:** multilingual quality, bias and spike false positives.
18. **Documents** — **WHAT:** versioned public/private files. **WHY:** official material searchable. **HOW:** upload to quarantine, scan, approve, then serve authorized download. **FILES:** document service and object adapter. **COMMANDS:** storage emulator/provider. **SECURITY:** private bucket, malware scan, signed URL expiry. **TESTING:** role access and malicious-file rejection.
19. **Payments** — **WHAT:** provider-hosted checkout and receipts. **WHY:** collect eligible municipal fees safely. **HOW:** integrate approved gateway with signed webhook/idempotency. **FILES:** payment adapter. **COMMANDS:** provider sandbox. **SECURITY:** no card/PIN/CVV storage; reconciliation and refund controls. **TESTING:** duplicate callbacks, failure, refund, ledger reconciliation.
20. **GIS/maps** — **WHAT:** ward, asset and complaint layers. **WHY:** spatial operational planning. **HOW:** PostGIS and configurable tiles/provider. **FILES:** spatial migration and map client. **COMMANDS:** PostGIS-enabled DB. **SECURITY:** household pins restricted; generalize public geometry. **TESTING:** permission by layer/zoom/export.
21. **Security** — **WHAT:** threat model and hardening baseline. **WHY:** sensitive public records need controlled access. **HOW:** review auth, RBAC, upload, backup, device flows. **FILES:** `docs/security/security.md`. **COMMANDS:** scanner commands in CI. **SECURITY:** secrets manager, TLS, rate limits, audit, incident response. **TESTING:** authorized security assessment before pilot.
22. **DevSecOps** — **WHAT:** quality/security gates. **WHY:** unsafe code doesn't promote silently. **HOW:** CI SAST, dependency/secret/IaC/container scans, DAST staging. **FILES:** `.github/workflows/ci.yml`. **COMMANDS:** pull request pipeline. **SECURITY:** protected branches, OIDC, signed artifacts. **TESTING:** verify intentionally vulnerable sample fails in isolated pipeline.
23. **Docker** — **WHAT:** reproducible containers. **WHY:** consistent builds. **HOW:** non-root minimal images, pinned base and health checks. **FILES:** `Dockerfile`, compose. **COMMANDS:** `docker compose up`. **SECURITY:** scan image, read-only fs, no embedded secrets. **TESTING:** startup/shutdown and image scan.
24. **Terraform** — **WHAT:** reviewed cloud infrastructure as code. **WHY:** repeatable least-privilege environments. **HOW:** remote encrypted state, modules, plan approval. **FILES:** `infra/terraform`. **COMMANDS:** `terraform fmt; terraform validate; terraform plan`. **SECURITY:** no state/secrets in git; OIDC and policy-as-code. **TESTING:** plan review and staging apply.
25. **Kubernetes** — **WHAT:** managed orchestration. **WHY:** controlled rollout/scale. **HOW:** probes, requests/limits, HPA, PDB, netpol, workload identity. **FILES:** `infra/kubernetes`. **COMMANDS:** `helm template` then reviewed deploy. **SECURITY:** restricted ingress/egress and secret refs. **TESTING:** rollout, node drain and rollback.
26. **Monitoring** — **WHAT:** metrics, structured logs, traces and alerts. **WHY:** detect service problems. **HOW:** OpenTelemetry and dashboards for latency, DB, queue, notifications, AI. **FILES:** ops dashboards (to add). **COMMANDS:** chart/provider-specific. **SECURITY:** redact personal fields, restrict security dashboard. **TESTING:** alert exercise and trace correlation.
27. **Testing** — **WHAT:** unit, integration, API, E2E, mobile, accessibility, load, security tests. **WHY:** critical workflows reliable. **HOW:** synthetic fixtures and isolated providers. **FILES:** `tests/` per package. **COMMANDS:** `pytest`, `pnpm lint`, app-specific suites. **SECURITY:** tenant isolation is a release gate. **TESTING:** cover registration, complaint workflow, roles, uploads, AI abstention and restore.
28. **Production release** — **WHAT:** staged, approved deployment. **WHY:** reduce outage risk. **HOW:** immutable digest, compatible migrations, canary and rollback. **FILES:** deploy workflows/runbook. **COMMANDS:** environment-specific release. **SECURITY:** protected environment approval and least privilege. **TESTING:** smoke, synthetic monitor, rollback rehearsal.
29. **Backup / DR** — **WHAT:** encrypted backup and recovery. **WHY:** recover records after incident. **HOW:** PITR, object versioning, periodic isolated restore. **FILES:** `docs/operations/disaster-recovery.md`. **COMMANDS:** provider-specific restore. **SECURITY:** separate backup credentials and immutable copy. **TESTING:** measure agreed RPO/RTO in exercise.
30. **Taluka / district** — **WHAT:** hierarchical expansion with aggregate access. **WHY:** reuse platform safely. **HOW:** parent organizations query federated/derived statistics. **FILES:** organization hierarchy and aggregate APIs. **COMMANDS:** migration/configuration rollout. **SECURITY:** parent roles never gain child PII automatically. **TESTING:** multi-level tenant isolation and aggregate reconciliation.
